# Участник 2: MCP-сервер — Евгений

Материал для подготовки Евгения к защите MCP-сервера. Прочитайте код, выполните проверки и адаптируйте рассказ к своему фактическому участию.

## За что отвечает участник

- `src/iacpaas_mcp/server.py`: регистрация инструментов и запуск транспорта.
- `src/iacpaas_mcp/schemas.py`: публичные типы результатов.
- `src/iacpaas_mcp/policy.py`: ограничения изменения и аудит.
- Тесты MCP-контракта, stdio/HTTP и запрета записи.

## Текст выступления

«Моя зона — MCP-сервер. MCP здесь является протоколом, а сервер — отдельной программой, которая предоставляет операции над графом клиентам. Сам сервер не решает, что хочет пользователь, и не требует подключения LLM.

При подключении клиент получает список инструментов и их схемы. Например, get_subgraph принимает путь ресурса, начальную вершину и глубину. Сервер проверяет аргументы, обращается к GraphService и возвращает структурированный результат. Если ресурс не существует или превышен лимит, клиент получает диагностируемую ошибку, а не случайную строку или ложный успешный ответ.

У сервера два режима. В stdio клиент сам запускает процесс и обменивается с ним сообщениями через стандартные потоки. Поэтому обычные логи нельзя писать в stdout. В HTTP-режиме сервер слушает localhost, а клиент обращается к /mcp с bearer-токеном. Инструменты и доменная логика в обоих случаях одинаковые.

Чтение и изменение разделены. Аннотация readOnlyHint помогает клиенту понять назначение инструмента, но не является защитой. Поэтому запись по умолчанию блокируется на сервере. Оператор должен отдельно разрешить её в конфигурации и указать допустимую область путей. Аргумент, который модель назвала подтверждением, не может включить это разрешение.

Мы выбрали явный policy gate, который допускается исходным заданием. Это не отдельная система одноразовых одобрений. После разрешения сервер доверяет авторизованным клиентам в пределах заданной области, поэтому такой учебный режим не нужно публиковать в интернет. В CLI есть ещё и запрос подтверждения человека.

Сейчас инструменты обращаются к тестовому backend. Это позволяет независимо проверить MCP, ошибки и безопасность. После подключения настоящей IACPaaS изменится адаптер данных, а не способ вызова инструментов агентом».

## Что показать в коде

1. Фабрику сервера и регистрацию двух читающих инструментов.
2. Как типизированная функция превращается в JSON Schema.
3. Обработку DomainError и флаг MCP isError.
4. Общую логику для двух транспортов.
5. Проверку политики перед изменением, отдельно от поведения агента.

## Что обязательно понимать

- MCP-сервер и агент — разные процессы с разными задачами.
- API IACPaaS и MCP API — разные интерфейсы: первый предоставляет платформа, второй делаем мы.
- Успешное соединение не доказывает правильность данных: нужны проверки результата.
- Клиентский вопрос «разрешить?» не защищает сервер от другого клиента.
- HTTP bearer-токен учебного стенда нельзя называть реализацией полного OAuth.
- Предел размера итогового ответа не заменяет предел загрузки из внешней платформы. Последний понадобится в реальном адаптере.

## Вопросы на защите

**Почему отдельный сервер, а не прямой вызов из агента?** Так одинаковыми операциями пользуются VS Code и Python-приложение. Схемы, политика и ошибки не дублируются в каждом клиенте.

**Почему два транспорта?** stdio удобен для локального запуска из IDE, HTTP позволяет подключаться к отдельно работающему процессу. Это требование задания.

**Кто выбирает инструмент?** В режиме LLM — модель через агентное приложение. На сервер приходит уже конкретное имя и аргументы.

**Можно обойти запрет прямым MCP-вызовом?** При выключенной серверной записи нельзя. Именно поэтому проверка находится на сервере, а не только в промпте агента.

**Почему не SDK v2?** Мы закрепили поддерживаемую линию v1.30 и проверили её API. Автоматическая смена основной версии без миграции может сломать импорты и поведение. Выбор версии описан в sources.md.
